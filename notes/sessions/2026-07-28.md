### DECISION [P]: elite transition proof via scenario-declared damage schedule

The flagged question, sanity-checked and settled. §2.11 binds proofs
to movement-only, fire-off AND ability-off; §3.5 demands a full-fight
proof ACROSS phase transitions; transitions ride HP%. So the harness
needs elite HP driven down without the bot touching fire. Mechanism:

- **`ScenarioDef.damage_schedule`** — optional array of
  `{tick, amount}` entries targeting the scenario's elite. Static
  scenario DATA, not a console command: deterministic,
  seed-independent, replay-visible by construction (a replay is
  scenario + seed + input log; per-tick state hashes cover HP), and
  the replay-dirty flag never enters the picture — god/console tools
  stay out of proofs, unchanged.
- Applied at exact tick equality through **THE one
  damage-resolution path** with source tag `test_schedule`
  (observable in the event stream / session.jsonl like any damage).
  Amounts are **final HP deltas (mitigation-bypassing)** so
  schedule→HP% mapping is exact and later armor retunes [T] cannot
  silently shift proof phase timing.
- **One mechanism, both proof tiers.** Per-phase pins = a single t0
  drop into the target HP band — the elite enters its phase through
  the REAL transition logic (no parallel force-phase hook to build
  or maintain). Full fight = a paced schedule at plausible Longbolt
  TTK stretched so every phase shows ≥2 full pattern cycles;
  transition ticks placed deliberately MID-VOLLEY (max in-flight
  overlap — the actual seam risk §3.5 exists to catch); final entry
  drives HP to 0 so the kill and post-death projectile/hazard
  cleanup are witnessed inside the proof window.
- Threshold semantics: phase swap resolves at damage application;
  if one application crosses multiple thresholds it settles at the
  final phase (test-only rapid-drop case; live fights cross one at
  a time).
- **Peak-density evidence goes mechanical**: the full-fight harness
  run records peak live hostile projectiles into the report JSON —
  ≤300 becomes a report field, with the in-play density meter as
  the visual counterpart.
- Guard: no tester-reachable scenario declares a damage_schedule —
  M7 pre-tester-build checklist line candidate (cheap to assert).
- Rejected: fire-enabled bot (violates §2.11 fire-off by
  construction; entangles aim/DPS policy with dodge evidence);
  console sethp/god (replay-dirty by design and invisible to the
  proof path); per-phase-only coverage (§3.5 names transitions
  explicitly — the seams are the point).
- Serialization: the schedule is static data applied by tick
  equality — no cursor state. **SERIAL 12 scope = elite phase state
  only**, deliberate golden regen at the bump.
